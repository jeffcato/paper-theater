# Compiler-bound production parent policy

INT-02 shared boundary, proposed services `pt-services-v1.12.0`. Runtime adoption, complete verification and exact-head CI remain pending until separately recorded. This policy describes permitted derivation; deserialized JSON and successful validation grant no issuance, execution, recovery or publication authority.

`ProductionConfigurationV1` remains an exact-request configuration. Its `request_sha256` is never a wildcard. The separate `ProductionParentPolicyV1` pins source/book, compiler, profile/recipe, operation stage/purpose/provider/project/model, inherited authorization/accounting, aggregate limits, compatible imported receipts and explicit recovery permission. It contains no predicted future request digest or unit ID.

`ProductionDerivationV1` binds one actual stage input and provider-v2 proposal to the exact original parent FileRef, compiler/source and purpose. `ProductionInputLineageV1` covers the union of committed stage/proposal inputs exactly. Conflicting aliases, omitted/extra/duplicate lineage, unrelated roots and diagnostic/synthetic input provenance fail. Autonomous inputs require the frozen compiler identity; imported inputs require an explicitly allowed original receipt. Their actual older compiler identity remains unchanged. Parent/derivation metadata stays 64 KiB, with bounded operation/receipt inventories. The ordinary logical-request cap remains 1 MiB.

Rust: `ProductionParentPolicyV1::validate()` and `validate_derivation(derived, original_policy_bytes, logical_request_bytes)`. TypeScript: `validateProductionParentPolicyV1` and asynchronous `validateProductionDerivationV1` with the same four arguments. Both read original policy/request bytes, require exact hashes and preserve omitted/null Option compatibility. These functions verify consistency, not whether a trusted compiler actually executed or a provider actually answered.

## Exact server adapter

1. Administrative startup separately authenticates operator authority and imports original balances, reservations, uncertain attempts and exhausted repairs. Freeze the original parent bytes privately. Resolve `accounting_scope_id` to the existing durable authorization ledger and provider/project quota scopes. Reject a second ID, policy alias, run or credential alias that would reset the same inherited limits. A new configuration hash is not additional money, requests or repairs.
2. Select the parent/scope from trusted registration. Freeze the actual compiler/build, complete source bytes, recipe/profile and active run/epoch. Invoke that compiler through the existing owned stage path; independently reconstruct lineage from committed provenance and exact CAS reads. Verify each producer/reuse receipt and its actual bytes, source root and compiler. Never pass a candidate-supplied lineage list through as trusted context.
3. Commit the actual logical request before issuance. Persist a child record binding original parent hash, stable accounting scope, selected operation scope, active stage/unit/epoch, compiler/source/purpose, all input receipt hashes, exact proposal/request and request bytes. Run the shared validator with independently selected original bytes. Provider/project/credential context comes from the frozen parent scope; the proposal cannot choose a different project.
4. Under the runtime's transaction/reservation boundary, recheck that registration, active epoch, all aggregate parent balances, applicable original quota windows and current repair/retry lineage remain valid. Issue the existing provider-v2 descriptor with this exact request hash. All children share the parent ledger; child ceilings are additional bounds. Keep original issued/request/raw identities and unknown charges through cancellation, restart, failure or interrupted settlement. Do not allocate another request identity to escape ambiguous work.
5. Existing-job recovery requires `allow_recovery` plus the existing independently issued query-only grant/observer. Select the latest genuine job selector; queries reserve requests without granting another creative repair. A recovery descriptor cannot submit new work. Preserve existing structured retry timing and the separate new-submission boundary.
6. Absent/unavailable parent support stays unavailable. Existing exact-request implementors, provider-v2 unavailable defaults and recovery APIs remain unchanged. No fallback to legacy provider/helper paths, credential loading, provider calls or synthetic acceptance is introduced.

The larger transcription audio-wire role is a separate remaining INT-02 request; this policy does not widen generic JSON/native-wire limits. Runtime authority, trusted provenance execution, actual media/reviews and the INT-06 publication migration still require their owning implementations. `production-verifier-pending` remains mandatory.
